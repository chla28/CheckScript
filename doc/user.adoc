== Présentation

`check-script` évalue un ou plusieurs scripts *shell* ou *Python 3* et
produit un *classement sur cinq catégories*, chacune notée sur 10 :

[cols="1,3",options="header"]
|===
|Catégorie |Ce qui est évalué
|Sécurité |Injection de commande, secrets en dur, téléchargements exécutés, permissions dangereuses, TLS désactivé, PATH non sûr, fichiers sensibles modifiés…
|Robustesse |Gestion des erreurs (`set -e`, `cd` non contrôlé, codes de retour ignorés), quoting, erreurs de syntaxe, CRLF…
|Maintenabilité |Lisibilité, style, formatage, taille des fonctions, imbrication, commentaires…
|Portabilité |Bashismes dans un script `/bin/sh` (dont ceux qui cassent sous dash), shebang, commandes obsolètes ou propres à une distribution…
|Performance |Processus inutiles (`cat \| grep`, `expr`, commandes externes dans les boucles…)
|===

Pour chaque catégorie, le rapport indique le *nombre de problèmes par
sévérité* (Critical / High / Medium / Low) et leur *total*, puis une *note
globale* et un niveau de A à E. Chaque problème est accompagné d'un *conseil
de correction* et, pour les outils externes, d'un lien vers leur
documentation.

L'outil exploite les analyseurs de référence lorsqu'ils sont installés
(ShellCheck, shfmt, bashate, checkbashisms, gitleaks, trufflehog, `bash -n`
pour le shell ; Ruff, Bandit, Semgrep, mypy, Radon, Vermin — et en option
Pylint, Pyright — pour Python, voir <<python>>) et les complète par des
*règles intégrées* qui fonctionnent toujours (64 pour le shell, 6 pour
Python).
Il sait aussi *corriger* les défauts sûrs (`--fix`), *comparer* deux analyses
(référence) et s'intègre à l'intégration continue (SARIF, GitLab Code
Quality, hook pre-commit). Une *interface graphique* (`check-script-gui`)
reprend le même moteur.

L'interface et les rapports sont disponibles en *français* et en *anglais*.

== Installation

=== Depuis l'archive

[source,bash]
----
tar xzf check_script-VERSION-linux-x86_64.tar.gz
cd check_script-VERSION-linux-x86_64
./install.sh              # installation utilisateur (~/.local)
sudo ./install.sh         # installation système (/usr/local)
./install.sh --prefix=/opt/outils
----

L'installation dépose la commande `check-script`, l'interface
`check-script-gui` (avec son entrée de menu), la page de manuel
(`man check-script`), les complétions bash et zsh et la documentation.
Désinstallation : `./uninstall.sh` (mêmes options).

Le binaire CLI est autonome ; l'interface nécessite GTK 3.

=== Paquets RPM

[source,bash]
----
sudo dnf install ./check-script-VERSION-1.fc44.x86_64.rpm       # CLI
sudo dnf install ./check-script-gui-VERSION-1.fc44.x86_64.rpm   # interface
----

Le paquet CLI recommande ShellCheck, shfmt et checkbashisms, installés
automatiquement si les dépendances faibles sont activées.

== Utilisation

[source,bash]
----
check-script mon_script.sh                          # rapport dans le terminal
check-script --details mon_script.sh                # + tous les problèmes et leur correction
check-script mon_script.sh -o rapport.html          # rapport HTML autonome
check-script -q deploy.sh -o r.md -o r.adoc         # fichiers seuls, rien à l'écran
check-script scripts/                               # tous les scripts d'un dossier
cat script.sh | check-script -                      # entrée standard
check-script --lang en build.sh                     # rapport en anglais
check-script --profile strict --context root install.sh
check-script --fix --dry-run deploy.sh              # corrections proposées (diff)
check-script --fix --backup deploy.sh               # corrections appliquées
check-script -b reference.json scripts/             # nouveaux problèmes seulement
check-script outil.py                               # script Python
check-script --python-target 3.6 --with pylint outil.py
----

Un *dossier* est parcouru récursivement ; y sont retenus les fichiers
`.sh`, `.bash`, `.ksh`, `.dash`, `.zsh`, `.py`, `.pyw` et les fichiers sans
extension dont le shebang désigne un shell ou Python. Les dossiers cachés
(`.git`, `.venv`…) et de dépendances (`venv`, `site-packages`,
`__pycache__`, `node_modules`) sont ignorés.

=== Options

[cols="2,5",options="header"]
|===
|Option |Effet
|`-o`, `--output FICHIER` |Écrit le rapport dans FICHIER ; format selon l'extension : `.md`, `.adoc`, `.html`, `.json`, `.sarif`, `.codeclimate.json` (ou `gl-code-quality-report.json`), `.txt`. Répétable.
|`-f`, `--format FORMAT` |`terminal`, `md`, `adoc`, `html`, `json`, `sarif`, `codeclimate` : format des fichiers sans extension reconnue, ou de la sortie standard sans `-o`.
|`-l`, `--lang fr\|en` |Langue du rapport. Défaut : `LC_ALL`, `LC_MESSAGES` puis `LANG`.
|`-s`, `--shell sh\|bash\|dash\|ksh\|zsh\|python` |Force le dialecte au lieu de le déduire du shebang (ou de l'extension `.py`).
|`--python-target VERSION` |Version minimale de Python que les scripts doivent supporter (défaut : `3.9`, voir <<python>>).
|`-p`, `--profile strict\|default\|legacy` |Profil de notation (voir <<profils>>).
|`--context root\|cron\|systemd\|interactive` |Contexte d'exécution (voir <<contextes>>). Répétable.
|`--follow-source` |Suit les fichiers sourcés (`shellcheck -x`).
|`-c`, `--config FICHIER` |Fichier de configuration YAML (voir <<config>>).
|`--with OUTIL` |Active un outil désactivé par défaut (`pylint`, `pyright`) ; répétable ou séparé par des virgules.
|`--without OUTIL` |Désactive un outil (`shellcheck`, `shfmt`, `bashate`, `checkbashisms`, `ruff`, `bandit`, `semgrep`, `mypy`, `radon`, `vermin`, `gitleaks`, `trufflehog`, `syntax`, `builtin`…) ; répétable ou séparé par des virgules.
|`--no-external` |N'utilise que les règles intégrées.
|`-b`, `--baseline RAPPORT.json` |Référence : seuls les nouveaux problèmes sont détaillés, l'évolution des notes est affichée (voir <<reference>>).
|`--fail-on-new SÉVÉRITÉ` |Avec `--baseline` : code de sortie 1 si un nouveau problème atteint cette sévérité.
|`--fix` |Corrige les défauts sûrs dans le fichier (voir <<fix>>).
|`--dry-run` |Avec `--fix` : affiche le diff unifié sans modifier le fichier.
|`--backup` |Avec `--fix` : conserve l'original en `FICHIER.orig`.
|`--details` |Terminal : tous les problèmes, avec leur conseil de correction (défaut : 10 par catégorie).
|`--summary` |Terminal : synthèse seule.
|`--[no-]source` |Terminal : affiche sous chaque problème la ligne de code concernée, avec un repère `^` sous la colonne signalée (défaut). Une ligne où un secret est détecté n'est jamais recopiée.
|`--[no-]color` |Force ou désactive la couleur (défaut : automatique, `NO_COLOR` respecté).
|`-q`, `--quiet` |Aucun rapport sur la sortie standard.
|`--fail-under NOTE` / `--fail-under CATÉGORIE=NOTE` |Code de sortie 1 si la note globale, ou celle d'une catégorie, est inférieure au seuil. Répétable ; plusieurs seuils séparés par des virgules (`security=8,robustness=6.5`) ; décimales avec un point.
|`--list-tools` / `--list-rules` |Outils détectés / règles intégrées.
|`-v`, `--version` / `-h`, `--help` |Version / aide.
|===

=== Codes de sortie

[cols="1,4",options="header"]
|===
|Code |Signification
|0 |Analyse effectuée.
|1 |Seuil non atteint (`--fail-under`, `--fail-on-new`).
|2 |Erreur d'usage (option invalide, aucun script, configuration ou référence invalide).
|3 |Script introuvable ou illisible, ou fichier de rapport impossible à écrire.
|===

Portabilité       10,0 ██████████            0        0        0        0       0

Détail des problèmes

  L3       Critical SEC002 [builtin]          Secret (mot de passe, jeton, clé) écrit en dur dans le script
        3 │ (ligne non reproduite : secret potentiel)

  L8       Critical SC2115 [shellcheck]       Use "${var:?}" to ensure this never expands to /* .
        8 │ rm -rf $APP_DIR/*
          │        ^
                                              → https://www.shellcheck.net/wiki/SC2115

----

Chaque problème indique sa *ligne* (`fichier` s'il concerne le script entier),
sa *sévérité*, sa *règle*, l'*outil* qui l'a détecté, le *code de la ligne*
(avec un repère `^` sous la colonne signalée quand l'outil la fournit ;
`--no-source` pour le masquer) et, avec `--details`, son *conseil de
correction* ou le lien vers la documentation de la règle. Une ligne où un
secret est détecté n'est jamais recopiée dans le rapport.
Les messages des outils externes restent en anglais ; ceux des règles
intégrées suivent `--lang`. Les *secrets* détectés ne sont jamais recopiés
dans le rapport.

=== Sévérités

[cols="1,4",options="header"]
|===
|Sévérité |Signification
|Critical |Compromission ou destruction probable (code téléchargé exécuté, secret en dur, `rm -rf /`, script syntaxiquement invalide).
|High |Défaut grave exploitable ou aux effets de bord importants (eval d'une variable, `chmod 777`, TLS désactivé, `cd` non contrôlé, bashisme qui casse sous dash).
|Medium |Défaut réel au comportement limité (variable non quotée, pas de `set -e`, fichier temporaire prévisible).
|Low |Style, lisibilité, performance, bonnes pratiques.
|===

=== Calcul des notes

Pour chaque catégorie :

----
note = 10 − Σ pénalités          (plancher 0, arrondi au dixième)

pénalité d'une règle déclenchée n fois = poids × (1 + log2 n)
poids (profil standard) : Critical 4 · High 2 · Medium 0,75 · Low 0,25
Medium et Low sont multipliés par √(100 / max(100, lignes de code))
----

* *Occurrences répétées* : une même règle déclenchée 8 fois coûte 4 fois son
  poids, pas 8 fois — des répétitions traduisent une seule habitude.
* *Taille du script* : au-delà de 100 lignes de code, les pénalités
  Medium/Low sont atténuées. Critical et High ne le sont jamais.

La *note globale* est la moyenne pondérée des catégories (Sécurité 1,5 ;
Robustesse 1,25 ; Maintenabilité 1 ; Portabilité 0,75 ; Performance 0,5),
*plafonnée à la plus faible note de catégorie + 1,5* : une catégorie faible
ne peut pas être masquée par les autres (principe du maillon faible).

Niveaux : *A* ≥ 9 · *B* ≥ 7,5 · *C* ≥ 6 · *D* ≥ 4 · *E* < 4.

Ces réglages ont été calibrés sur un corpus de scripts réels et typiques
(voir le guide développeur).

=== Doublons entre outils

Quand plusieurs outils signalent le même défaut sur la même ligne (par
exemple ShellCheck SC2002 et la règle intégrée PERF001), un seul problème
est conservé, celui de l'outil le plus spécialisé : `bash -n`, ShellCheck,
gitleaks, trufflehog, checkbashisms, règles intégrées, shfmt, bashate. En
Python : compilation, Bandit, Ruff, Semgrep, mypy, Pyright, Pylint, Vermin,
Radon, puis gitleaks, trufflehog et règles intégrées.

[[profils]]
== Profils

[cols="1,4",options="header"]
|===
|Profil |Usage
|`strict` |Nouveaux scripts : poids Critical 5, High 3, Medium 1, Low 0,4 ; atténuation dès 50 lignes ; lignes ≤ 100, fonctions ≤ 40 lignes, imbrication ≤ 3.
|`default` |Réglages décrits ci-dessus.
|`legacy` |Existant ancien : High 1,5, Medium 0,5, Low 0,1 ; seuils relâchés ; règles de pur style désactivées (MNT001, MNT004, MNT005, MNT010, formatage shfmt et Ruff, E001–E006 de bashate ; en Python PYMNT001, E501, W291, W293, C0301, C0303).
|===

Le profil se choisit par `--profile` ou par la clé `profile:` de la
configuration ; les autres clés de la configuration s'appliquent par-dessus.

[[contextes]]
== Contextes d'exécution

Déclarer comment le script est lancé active des règles spécifiques et
relève certaines sévérités (elles ne sont jamais abaissées) :

[cols="1,3,3",options="header"]
|===
|Contexte |Règles activées |Sévérités relevées
|`root` |SEC017 (PATH non fixé) |fichier temporaire prévisible, téléchargement en clair, `source` non fiable, archive non vérifiée → High ; `chmod 777`, `rm -rf "$VAR/"`, `cd` non contrôlé → Critical ; pas de `set -e` → High
|`cron` |ROB014 (pas de verrou), ROB015 (saisie interactive), ROB016 (PATH non fixé) |pas de `set -e`, fichier temporaire prévisible → High ; `set -x` → Medium
|`systemd` |SEC017, ROB015 |pas de `set -e` → High ; `set -x` → Medium
|===

[[directives]]
== Directives dans le script

Un faux positif ou un choix assumé se neutralise dans le script lui-même :

[source,bash]
----
#!/bin/bash
# check-script disable-file=MNT005,E003        # tout le fichier

# check-script disable=SEC005                  # commentaire seul : ligne de code suivante
curl -k "$URL_INTERNE"

eval "$SAFE_CMD"  # check-script disable=SEC003   # cette ligne
# check-script disable-next-line=SEC022
CLE_PUBLIQUE="AAAAC3NzaC1lZDI1NTE5AAAAI…"
----

Les identifiants acceptent le joker final (`SC20*`) et `all`. Le nombre de
problèmes neutralisés figure dans le rapport. Les directives
`# shellcheck disable=…` restent traitées par ShellCheck.

[[fix]]
== Correction automatique

`--fix` applique uniquement des transformations *sûres* :

. les corrections proposées par ShellCheck (quoting de variables,
  `cd … || exit`, backticks…) ;
. les corrections intégrées : fins de ligne CRLF, espaces finaux, backticks
  → `$(…)`, `egrep`/`fgrep` → `grep -E`/`-F`, `which` → `command -v`,
  `read` → `read -r` (jamais dans un heredoc, une chaîne ou un commentaire) ;
. le formatage shfmt, dans le style d'indentation du script.

Le résultat est contrôlé par `bash -n` (ou `sh -n`) : si le script était
valide et ne le serait plus, *aucune* correction n'est écrite. Le rapport
affiché ensuite porte sur la version corrigée.

[source,bash]
----
check-script --fix --dry-run deploy.sh       # diff sur la sortie standard, rien n'est écrit
check-script --fix --backup deploy.sh        # écrit deploy.sh, garde deploy.sh.orig
----

[[code-correction]]
=== Code de correction par problème

Pour chaque problème, l'interface graphique (en dépliant le problème) et le
rapport HTML montrent le code à écrire :

* *Correction proposée* : les lignes concernées avant et après correction,
  quand une correction sûre existe pour ce problème précis (proposition de
  ShellCheck, ou correction intégrée limitée à la ligne) ; dans l'interface,
  *Appliquer cette correction* modifie uniquement ces lignes (contrôle
  `bash -n`, refus si le fichier a changé depuis l'analyse) ;
* sinon, *Exemple de correction* : un exemple générique « à éviter / à
  écrire » de la règle (toutes les règles intégrées et les codes ShellCheck
  les plus courants).

Toute correction depuis l'interface (*Corriger…* ou *Appliquer cette
correction*) sauvegarde le script en `.orig` à la première correction depuis
le lancement ; les corrections suivantes conservent cette copie, qui reste
donc le script d'avant la première correction.

Le bouton *Copier* place le code corrigé dans le presse-papiers. Une ligne
où un secret est détecté ne reçoit jamais de correction concrète (son
aperçu recopierait le secret).

[[reference]]
== Référence et évolution

Un rapport JSON antérieur sert de *référence* : seuls les problèmes
nouveaux sont détaillés, et l'évolution des notes est affichée
(`nouveaux : 1 · corrigés : 2 · inchangés : 30`, `Note globale : 6,1 → 7,4
(+1,3)`). Les problèmes sont appariés par une empreinte indépendante du
numéro de ligne : ajouter du code au-dessus d'un problème connu ne le fait
pas passer pour nouveau.

[source,bash]
----
check-script -q -o reference.json scripts/          # sur la branche principale
check-script -b reference.json --fail-on-new high scripts/
----

C'est la manière d'adopter l'outil sur un existant : la dette actuelle est
tolérée, toute nouvelle dette bloque.

== Outils externes : ce qui est exploité

ShellCheck::
JSON avec les vérifications optionnelles `add-default-case`,
`avoid-nullary-conditions`, `check-set-e-suppressed`,
`check-unassigned-uppercase`, `deprecate-which`, `useless-use-of-cat`.
Chaque code SCxxxx est classé (SC2115 → Sécurité/Critical, SC2164 →
Robustesse/High, SC3xxx → Portabilité, bashismes qui cassent sous dash →
High…). `SC1091` est exclu par défaut. Ses corrections alimentent `--fix`.

shfmt::
Formatage contrôlé dans le style d'indentation du script (le choix du style
n'est pas pénalisé, ses incohérences le sont). Son *arbre syntaxique*
(`--to-json`) rend exactes les règles intégrées qui portent sur des
commandes (un `which` dans une chaîne n'est pas une commande ; un `mkdir`
dans la condition d'un `if` est contrôlé).

bashate::
Style ; E003 ignoré pour un script indenté autrement que par 4 espaces.

checkbashisms::
Scripts `/bin/sh` (ou sans shebang) uniquement.

gitleaks, trufflehog::
Détection de secrets ; trufflehog est lancé avec `--no-verification` pour
qu'aucun secret ne soit envoyé sur le réseau.

bash -n::
Contrôle syntaxique avec l'interpréteur du dialecte : toute erreur est
Critical.

== Règles intégrées

Liste complète : `check-script --list-rules`. Chaque règle a un conseil de
correction (affiché avec `--details` et dans les rapports fichiers). Entre
crochets : règle active seulement dans ce contexte.

[cols="1,2,1,6",options="header"]
|===
|Règle |Catégorie |Sévérité |Description
|SEC001 |Sécurité |Critical |Contenu téléchargé exécuté directement par un shell (`curl \| sh`, `bash <(curl …)`)
|SEC002 |Sécurité |Critical |Secret écrit en dur (mot de passe, jeton, clé AWS/GitHub, clé privée)
|SEC003 |Sécurité |High |`eval` appliqué à une expansion : risque d'injection
|SEC004 |Sécurité |High |Permissions en écriture pour tous (`chmod 777/666`, `o+w`)
|SEC005 |Sécurité |High |Vérification TLS / clé d'hôte désactivée
|SEC006 |Sécurité |Medium |Téléchargement en clair (`http://`)
|SEC007 |Sécurité |High |`rm -r` sur un chemin construit avec une variable non protégée
|SEC008 |Sécurité |Critical |Suppression récursive de `/` ou d'un répertoire système
|SEC009 |Sécurité |Medium |Fichier temporaire au nom prévisible dans `/tmp`
|SEC010 |Sécurité |High |Mot de passe en ligne de commande (`sudo -S`, `sshpass -p`, `mysql -pXXX`…)
|SEC011 |Sécurité |Medium |`source` d'un fichier depuis `/tmp` ou une URL
|SEC012 |Sécurité |Low |`set -x` : secrets dans les journaux
|SEC013 |Sécurité |High |Bit setuid/setgid
|SEC014 |Sécurité |Medium |Saisie d'un secret sans masquage (`read` sans `-s`)
|SEC015 |Sécurité |Low |`sudo` avec une commande relative, PATH non fixé
|SEC016 |Sécurité |High |PATH contenant `.` ou une entrée vide

== Scripts Python

Un script est traité comme *Python 3* quand son shebang désigne `python`,
`python3` ou `python3.N` (y compris via `env`), ou, sans shebang, quand son
extension est `.py` / `.pyw` ; `--shell python` le force. Les outils shell
ne sont alors pas lancés, et inversement : le rapport ne liste que les
outils du langage du script (plus gitleaks, trufflehog et les règles
intégrées, communs aux deux).

=== Outils et classement

Ruff::
Familles retenues : `E4`, `E7`, `E9`, `E501`, `W`, `F`, `B`, `S`, `UP`,
`PERF`, `C4`, `SIM`, `BLE`, `PLE`, `PLW`, `PLR`, `PIE`, `RUF`, `EXE`,
`T10`, `ISC`, `A`, `ASYNC` (les familles de pur style — docstrings,
annotations, nommage — sont écartées). `PLR2004` (constantes « magiques ») et
`S603` sont exclus par défaut. Lancé avec `--isolated` : la configuration
Ruff du projet n'influence pas la note. Chaque famille est classée (`S` →
Sécurité, `F` → Robustesse, `PERF` / `C4` → Performance, `EXE` →
Portabilité…), avec des reclassements (`F821` nom non défini → High, `S602`
`shell=True` → High…). `ruff format --diff` signale les écarts de
formatage. Seules les corrections qualifiées de *sûres* par Ruff sont
proposées.

Bandit::
Sévérité de Bandit, abaissée d'un cran si sa confiance est faible ; secrets
en dur (`B105`–`B107`) relevés en High, leur valeur n'étant jamais recopiée
dans le rapport. `B404` et `B603` (tout import ou appel de subprocess) sont
exclus par défaut.

Semgrep::
Règles du registre `p/python`, lancées avec `--metrics=off`. *Un accès
réseau à semgrep.dev est nécessaire* : hors ligne, l'outil est marqué « échec »
et l'analyse se poursuit sans lui (le désactiver sur un poste isolé).

mypy::
Lancé avec `--check-untyped-defs` (les fonctions non annotées sont aussi
vérifiées) et `--ignore-missing-imports`, sans cache sur disque. Les erreurs
de typage sont classées Robustesse / Medium. mypy 2 n'accepte plus de cible
inférieure à 3.10 : il vérifie alors avec la version de l'interpréteur,
Vermin couvrant la portabilité.

Radon::
Fonctions de complexité cyclomatique ≥ 11 (rang C → Low, D → Medium, E-F →
High) ; indice de maintenabilité de rang B (Low) ou C (Medium).

Vermin::
Chaque construction qui exige une version de Python supérieure à la cible
(ex. `match` → 3.10) : Portabilité / High, le script ne s'exécuterait pas.

Pylint, Pyright::
Désactivés par défaut car redondants avec Ruff et mypy ; `--with pylint`,
`--with pyright`, la configuration YAML ou les réglages de l'interface les
activent. `C0103` et `C0114`–`C0116` (nommage, docstrings) sont exclus de
Pylint par défaut.

Les doublons entre outils sont fusionnés sur une même ligne : `S602` (Ruff)
= `B602` (Bandit) = `subprocess-shell-true` (Semgrep), `PLW0602` (Ruff) =
`W0602` (Pylint), erreurs mypy = erreurs Pyright…

=== Version cible

`pythonTarget` (défaut `3.9`, le Python de RHEL / Rocky 9 ; option
`--python-target`, réglage de l'interface) est transmis à Vermin, Ruff
(`--target-version`), Pylint et Pyright. Dans le YAML, la version s'écrit
entre guillemets : `3.10` sans guillemets serait lu comme le nombre 3.1.

=== Correction

`--fix` (et *Corriger…* dans l'interface) applique les corrections sûres de
`ruff check --fix` puis `ruff format` ; le résultat est contrôlé par la
compilation Python. Les directives `# check-script disable=…` s'utilisent
comme en shell ; les commentaires `# noqa` restent respectés par Ruff.

== Configuration

Fichier YAML lu, dans l'ordre : `--config FICHIER`, `./.checkscript.yaml`,
`${XDG_CONFIG_HOME:-~/.config}/check-script/config.yaml`. Toutes les clés sont
facultatives ; exemple commenté : `doc/checkscript.example.yaml`.

[source,yaml]
----
profile: strict                        # base : strict | default | legacy
context: [root]                        # contextes d'exécution
followSource: true                     # shellcheck -x
pythonTarget: "3.11"                   # Python minimal (entre guillemets)
tools:
  shellcheck:
    path: /opt/shellcheck/shellcheck
    exclude: [SC1091, SC2034]
  bashate: false                       # désactive l'outil
  semgrep: false                       # poste sans accès réseau
  pylint: true                         # active un outil désactivé par défaut
  ruff:
    exclude: [PLR2004, S603, E501]     # transmis à ruff --ignore
rules:
  disabled: [MNT005, E006]             # règles ignorées, tout outil confondu
  overrides:
    SC2086: { category: security, severity: medium }
scoring:
  weights: { critical: 4, high: 2, medium: 0.75, low: 0.25 }
  referenceLines: 100
  categoryWeights: { security: 1.5, performance: 0.5 }
thresholds:
  maxLineLength: 100
  maxFunctionLines: 60
  maxNesting: 4
  maxLinesWithoutFunction: 150
----

== Interface graphique

`check-script-gui` (menu « CheckScript », ou lanceur MainGUI de la suite
AuditTools) reprend le même moteur, les mêmes règles et les mêmes rapports :

* *Analyse* : ouvrir ou déposer un script ; source annoté (marque de
  sévérité en marge, info-bulle des problèmes), onglet *Synthèse* (note
  globale, radar des cinq catégories, compteurs par sévérité) et onglet
  *Problèmes* (filtres par catégorie et sévérité, conseil, lien vers la
  documentation ; un clic place le source sur la ligne et déplie le code à
  écrire, voir <<code-correction>>) ; la barre entre le code et les
  résultats se déplace à la souris (double-clic : répartition par défaut),
  ses flèches replient l'un ou l'autre panneau ; la répartition est
  mémorisée, séparément pour une fenêtre large (côte à côte) et étroite
  (l'un au-dessus de l'autre) ;
* *Corriger…* : aperçu du diff puis application ;
* *Règles* : toutes les règles de détection — règles intégrées, codes des
  outils classés par l'outil (ShellCheck, Ruff, Bandit, Pylint…) et codes
  rencontrés lors des analyses —, chacune avec une case à cocher : une règle
  décochée n'est plus signalée *à partir de l'analyse suivante* (bouton
  *Relancer l'analyse*). Recherche par code, texte ou outil ; filtres par
  langage, outil et catégorie ; champ pour désactiver n'importe quel autre
  code (ex. `SC2317`) ; *Tout réactiver*. Les règles désactivées par le
  profil ou le fichier YAML apparaissent décochées et grisées. Dans la liste
  des problèmes, un problème déplié propose aussi *Ne plus signaler* sa
  règle. Une règle est désactivée par son identifiant, tout outil confondu,
  comme `rules.disabled` de la configuration ; le choix est mémorisé ;
* *Dossier* : tableau triable de tous les scripts d'un dossier ; avec une
  référence chargée, colonne *Tendance* (évolution de la note) ;
* *Exporter…* : HTML, Markdown, AsciiDoc, JSON, SARIF ;
* *Réglages* : langue, thème, profil, contextes, outils groupés par langage
  (avec détection des versions ; Pylint et Pyright activables), version
  minimale de Python, suivi des fichiers sourcés, fichier de configuration
  YAML.

La progression outil par outil s'affiche pendant l'analyse, qui peut être
annulée. Un chemin passé en argument (`check-script-gui deploy.sh` ou un
dossier) est analysé au démarrage.

== Questions fréquentes

Le rapport dit « Outils absents » ::
L'analyse s'est limitée aux règles intégrées pour ces outils ; installez-les
pour un résultat complet (`check-script --list-tools` donne les commandes).

Mon script est en bash mais n'a pas de shebang ::
Utilisez `--shell bash` ; sans shebang, le dialecte est inconnu, POR001 est
signalé et checkbashisms est exécuté en mode forcé.

Comment ignorer une règle pour un seul script ? ::
Par une directive `# check-script disable=…` / `disable-file=…` (voir
<<directives>>), ou `# shellcheck disable=…` pour les codes ShellCheck.

Pourquoi un script POSIX avec quelques bashismes est-il noté si bas ? ::
Parce qu'il échouera réellement sur les systèmes où `/bin/sh` est dash
(Debian, Ubuntu) : `function`, `[[`, `&>`, `<<<` ou les tableaux y sont des
erreurs, pas des détails de style. Déclarez `#!/usr/bin/env bash` si le
script est écrit pour bash.
