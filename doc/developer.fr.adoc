== Vue d'ensemble

`check-script` est une bibliothèque Dart (`lib/`) exposée par un CLI
(`bin/check_script.dart`) et une interface Flutter (`gui/`). Elle orchestre
des analyseurs de scripts shell et Python 3 (outils externes et règles
intégrées),
normalise leurs résultats en *problèmes* (`Finding`) classés par catégorie et
sévérité, les dédoublonne, applique directives, contextes et configuration,
calcule les notes et produit les rapports. Elle sait aussi corriger les
défauts sûrs et comparer une analyse à une référence.

=== Principes

* *Exploiter les outils existants* (ShellCheck, shfmt, bashate,
  checkbashisms, gitleaks, trufflehog, `bash -n`) plutôt que les réécrire ;
  les règles intégrées couvrent ce qu'ils ne traitent pas et assurent une
  analyse minimale sans eux.
* *Dégradation gracieuse* : un outil absent est signalé, jamais bloquant ;
  sans shfmt, les règles structurelles retombent sur un lexer heuristique.
* *Bibliothèque d'abord* : `lib/` n'écrit jamais sur la console ; le CLI et
  l'interface ne sont que des façades.
* *Testabilité* : l'exécution des commandes passe par `CommandRunner`
  (remplacé par un faux dans les tests) ; les parseurs sont des fonctions
  pures testées sur des sorties *réelles* enregistrées ; un corpus fige le
  comportement sur des scripts réels.
* *Pas de fuite de secrets* : jamais recopiés dans les rapports, trufflehog
  lancé sans vérification réseau.

== Flux d'analyse

----
fichier ──► ScriptInfo.fromContent (shebang ou extension .py → Dialect, CRLF, lignes)
              │
              ▼
Engine.analyze ── pour chaque Analyzer du langage du script (analyzersFor),
              │   activé, dans l'ordre de priorité :
              │     shell  : syntax → shellcheck → gitleaks → trufflehog → checkbashisms
              │              → builtin (arbre shfmt si disponible) → shfmt → bashate
              │     python : syntax → bandit → ruff → semgrep → mypy → pyright → pylint
              │              → vermin → radon → gitleaks → trufflehog → builtin (ast)
              │     outils lancés en parallèle (Future.wait), résultats rangés dans
              │     l'ordre de priorité ; Engine(parallel: false) pour l'ordre strict
              │     onProgress(AnalysisProgress) ; CancelToken vérifié à chaque outil
              │   analyzeFiles(paths, jobs) : plusieurs scripts à la fois (défaut
              │     Engine.defaultJobs = processeurs / 4, entre 1 et 4), ordre conservé
              ▼
deduplicate   ── garde le premier de chaque groupe de doublons
Suppressions  ── directives # check-script disable… (comptées dans `suppressed`)
enrich        ── liens de documentation, conseils génériques des outils externes
escalate      ── sévérités relevées selon les contextes (root, cron, systemd)
applyConfig   ── rules.disabled, rules.overrides
fingerprintAll── empreintes stables (baseline, SARIF, Code Quality)
sortFindings  ── catégorie, sévérité, ligne
scoreCategory × 5, globalScore
              ▼
ScriptReport ──► Baseline.compare (si référence) ──► render(format)
----

== Modèle

`Finding`:: `tool`, `ruleId`, `category`, `severity`, `line` (0 = fichier),
`column`, `message`, `snippet`, `equivalents` (codes d'autres outils
désignant le même défaut), `hint` (conseil), `url` (documentation),
`fingerprint`, `endLine` (fin de l'instruction multi-ligne signalée, pour
le dédoublonnage : recouvrement de lignes, étendue ≤ `maxDuplicateSpan`),
`edits` (correction concrète : `TextEdit` 1-based, fin
exclusive ; issue du `fix` ShellCheck ou de `attachFixes` pour les
corrections intégrées). `Finding.fromJson` relit `toJson`.
`fixPreview` en tire les lignes avant / après ; `exampleFor`
(`rules/examples.dart`) donne l'exemple générique d'une règle.

`ToolRun`:: `ok`, `missing`, `skipped`, `failed`, `disabled` ; version ;
nombre de problèmes ; `detail` (`ast` / `lexer` pour les règles intégrées).

`ScriptReport`:: script, outils, problèmes, 5 `CategoryScore`, note globale,
niveau, date, `suppressed`, `profile`, `contexts`, `comparison`.

== Analyseurs

[source,dart]
----
abstract class Analyzer {
  String get name;                                   // clé de configuration
  ToolLanguage get language;                         // shell (défaut), python ou any
  Future<AnalyzerResult> analyze(AnalysisContext ctx);
  Future<String?> version(CommandRunner runner, CheckConfig config); // null = absent, '?' = illisible
}
----

`CommandRunner.run(exe, args, {stdin, cancel})` renvoie `null` si
l'exécutable est introuvable. `ProcessCommandRunner` force `LC_ALL=C`, écrit
`stdin` (utilisé par `shfmt --to-json`, `bash -n`, le formatage de `--fix`)
et tue le processus quand le `CancelToken` est déclenché. Les analyseurs
passent par `ctx.run(...)`, qui transmet le jeton.

=== Classement des codes ShellCheck

`shellcheckMap` classe explicitement les codes significatifs ; sinon
`classifyShellcheck` applique : SC3xxx → Portabilité (Medium/Low), SC1xxx
`error` → Robustesse/High, `style` → Maintenabilité/Low, sinon Robustesse
selon le niveau. Les bashismes qui *cassent sous dash* (SC2112/2113
`function`, SC3010 `[[`, SC3011 `<<<`, SC3020 `&>`, SC3030/3054 tableaux,
SC3005/3006 `((`, SC3018, SC3001) sont High — décision issue du calibrage.

=== Dédoublonnage

Deux problèmes sont doublons si l'un des `equivalents` de l'un correspond au
`ruleId` de l'autre (exact ou préfixe `*`) et qu'ils portent sur la même
ligne — ou que l'un est « fichier » (ligne 0) ou une erreur `SYNTAX`. Même
outil : même ligne et (même règle ou équivalent). Le premier rencontré est
conservé ; l'ordre de `defaultAnalyzers()` fixe la priorité.

=== Équivalences Python

Ruff `Snnn` = Bandit `Bnnn` (mêmes numéros) ; Ruff `PLxnnnn` = Pylint
`xnnnn` ; table `_ruffToPylint` pour les autres (`E722` = `W0702`, `B006` =
`W0102`…) ; Semgrep équivaut aux codes Bandit et Ruff de sécurité de la même
ligne ; mypy aux diagnostics Pyright (`report*`) ; les erreurs de *version*
(`match` en 3.9) de Ruff et Pyright sont classées Portabilité et équivalent
à `VERMIN`. Les messages Bandit B105–B107 et Semgrep « secret » sont
caviardés, et leurs lignes masquées (`_revealsSecret`).

== Règles intégrées

=== Catalogue

`rules/catalog.dart` décrit chaque règle : identifiant, catégorie, sévérité,
titre et *conseil de correction* bilingues (`Tr`), contextes d'activation.
La détection est séparée (`builtin_rules.dart`) ; `add(id, line, …)` y crée
le `Finding` à partir du catalogue et ignore les règles dont le contexte
n'est pas déclaré.

=== Arbre syntaxique (shfmt) et repli lexer

`AstFacts` (`analyzers/ast.dart`) parcourt le JSON de `shfmt --to-json` :

* `functions` : nom, lignes de début et de fin ;
* `blocks` : structures de contrôle et profondeur (else/elif au même niveau) ;
* `commands` : nom littéral, arguments littéraux (`null` si expansion),
  `hasExpansion`, `checked` (condition de if/while, opérande gauche de `&&`
  / `||` — opérateurs 10 et 11 —, commande niée), `inLoop`,
  `inSubstitution`.

Avec l'arbre, les règles de commande (SEC003, SEC012, ROB005, ROB007,
ROB011, POR004, POR005, POR007, PERF003, PERF004) et structurelles (MNT002,
MNT003) sont exactes ; les `LineRule` marquées `astCovered` sont alors
ignorées. Sans shfmt, `lexScript` (commentaires, chaînes masquées dans
`bare`, heredocs) et les expressions régulières prennent le relais.

=== Ajouter une règle

. Ajouter une `RuleInfo` dans `ruleCatalog` (titre et conseil fr/en,
  contextes éventuels).
. Ajouter sa détection : une `LineRule` dans `lineRules` (avec
  `equivalents`, et `astCovered` + un cas dans `_astStructure` si elle porte
  sur une commande), ou une règle fichier dans `runBuiltinRules`.
. Si elle doit être relevée dans un contexte, compléter
  `contextEscalations`.
. Tests : un cas déclencheur et un cas sain (`builtin_rules_test.dart` ou
  `new_rules_test.dart`), puis `UPDATE_GOLDEN=1 dart test test/corpus_test.dart`
  si le corpus change — en vérifiant chaque écart.
. Mettre à jour le tableau des règles de `doc/user.fr.adoc`.

== Directives, contextes, profils

* `Suppressions.parse` lit `# check-script disable=` (ligne, ou ligne de code
  suivante pour un commentaire seul), `disable-next-line=`, `disable-file=` ;
  jokers `*` et `all`.
* `ExecContext` (`root`, `cron`, `systemd`) : règles conditionnelles
  (`RuleInfo.contexts`) et `contextEscalations` (sévérité seulement relevée).
* `Profile` : `CheckConfig.forProfile` fournit la base ; `CheckConfig.parse`
  applique le YAML par-dessus (le profil de la ligne de commande prime sur la
  clé `profile:`).

== Notation et calibrage

----
facteur(n)  = √(référence / max(référence, lignes de code))       référence = 100
pénalité    = Σ_règles poids(sévérité) × (1 + log2 occurrences) × (facteur si Medium/Low)
note        = clamp(10 − pénalité, 0, 10), arrondie au dixième
globale     = min(moyenne pondérée, pire catégorie + 1,5)            maxGapToWorst
niveau      = A ≥ 9, B ≥ 7,5, C ≥ 6, D ≥ 4, E
----

Le *corpus* `test/corpus/` réunit des copies figées de scripts de la suite
AuditTools et des scripts typiques (installeur `curl | bash`, sauvegarde
cron ancienne, script init POSIX avec bashismes, bibliothèque propre), et
12 scripts Python `py_*` écrits pour le calibrage (outil propre, client
d'API négligent, installeur dangereux, style Python 2, fonctionnalités
3.10+…). Semgrep est écarté du contrôle des niveaux (règles téléchargées).
`labels.yaml` donne pour chacun, *établi a priori en lisant le script*, la
plage de niveaux attendue (avec et sans contexte), les règles obligatoires
et interdites.

[source,bash]
----
dart run tool/calibrate.dart --details     # notes réelles vs plages attendues
----

Deux ajustements en sont issus : bashismes cassant dash classés High, et
plafond de la note globale ramené de « pire + 2,5 » à « pire + 1,5 ». Tout
changement de poids doit laisser le corpus conforme.

Le calibrage Python (0.7.0) a aligné les sévérités sur l'échelle shell sans
toucher au modèle : secrets en dur Critical si la valeur est réaliste (comme
SEC002), exécution de code ou de données High (comme SEC003), PYSEC001
Medium (comme SEC022), shebang `python` High ; il a ajouté PYROB003 (cron
sans verrou, comme ROB014) et PYROB004 (code de retour de `main()` perdu),
et compte les docstrings comme de la documentation. Trois plages *a priori*
jugées trop sévères au regard de l'échelle shell ont été révisées, avec leur
justification dans `labels.yaml`.

== Correction automatique

`fixScript` enchaîne : remplacements ShellCheck (`parseShellcheckFixes`,
`applyEdits` : positions 1-based, fin exclusive, tabulation = 1 colonne,
éditions en conflit ignorées), corrections intégrées (`applyBuiltinFixes`,
jamais dans un heredoc, une chaîne multi-lignes ou un commentaire ;
`replaceBackticks` ignore les apostrophes et les backticks échappés), puis
`shfmt -ln -i` sur l'entrée standard. Si `<shell> -n` accepte l'original mais
refuse le résultat, `FixResult.aborted` est renseigné et rien n'est écrit.
Pour un script Python (`_fixPython`) : `ruff check --fix` puis `ruff format`
sur l'entrée standard (`--stdin-filename=script.py`), les corrections étant
comptées d'après la sortie JSON ; contrôle par la compilation Python
(`syntaxRegression` utilise `SyntaxAnalyzer.commandFor`).
`unifiedDiff` (Myers) produit le diff de `--dry-run` et de l'interface.

== Référence (baseline)

`fingerprintAll` calcule `fnv1a64(outil|règle|ligne normalisée|rang)` : le
numéro de ligne n'entre pas dans l'empreinte. `Baseline.parse` relit un
rapport JSON ; `compare` apparie par empreinte (multiensemble) et renvoie
`Comparison` (nouveaux, corrigés, inchangés, notes précédentes). Les rapports
ne détaillent alors que les nouveaux problèmes (`detailFindings`).

== Rapports

`render(reports, format, RenderOptions)` ; `OutputFormat` : `terminal`,
`markdown`, `asciidoc`, `json`, `sarif`, `html`, `codeclimate` (déduit de
l'extension par `OutputFormat.fromPath`).

* SARIF : une règle par couple outil/règle (`help`, `helpUri`,
  `security-severity` pour la sécurité), résultats avec
  `partialFingerprints`, `startLine ≥ 1`.
* Code Quality : `check_name`, `severity` (blocker/critical/major/minor),
  `fingerprint`, `location.lines.begin`.
* HTML : page unique sans ressource externe, thème clair/sombre, filtres,
  source annotée (ancres `#s<i>-L<n>`).

== Commits et publication

Les messages de commit suivent les
https://www.conventionalcommits.org/fr/[Conventional Commits] : types,
portées et description en anglais (l'historique jusqu'à 0.18.5 est en
français), sans point final, première
ligne de 100 caractères au plus.

[source]
----
feat(gui): ajoute l'onglet Règles
fix(flatpak): lance les outils par leur chemin absolu
docs(user): précise --changed-since
feat(engine)!: change le format JSON        ← « ! » ou « BREAKING CHANGE: » : incompatible
----

Types : `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`,
`style`, `chore`, `revert`. Portées usuelles : `engine`, `cli`, `gui`,
`python`, `rules`, `reporters`, `flatpak`, `appimage`, `rpm`, `ci`, `doc`.

* *Contrôle local* : `scripts/install-git-hooks.sh` active `.githooks/`
  (`core.hooksPath`) ; le hook `commit-msg` refuse un message non conforme
  (`git commit --no-verify` pour passer outre).
* *Contrôle CI* : `.github/workflows/commits.yml` vérifie les nouveaux
  commits de chaque push et pull request (`tool/commit_lint.dart --range`).
* *Publication* : `dart run tool/release.dart --dry-run` affiche la version
  suivante et la section du CHANGELOG ; sans `--dry-run`, synchronise les
  fichiers de version, écrit le CHANGELOG, commite `chore(release): X.Y.Z`
  et tague `vX.Y.Z` (`--push` pour pousser, ce qui déclenche la publication
  GitHub). Version : `feat` → mineure, autre changement → correctif,
  incompatible → majeure (mineure tant que la version est 0.x). Les notes
  rédigées sous « ## Unreleased » sont gardées en tête de la section.

== Build et packaging

`scripts/build-dist.sh [VERSION] [--rpm] [--install] [--skip-tests] [--no-gui]`
(appelé aussi par l'orchestrateur `AuditTools/scripts/build-dist.sh`) :
analyse et tests (Dart et Flutter), binaire CLI, bundle Flutter (version
injectée par `--build-name`), page de manuel (asciidoctor), complétions,
documentation et exemples CI, `.desktop` et icône, SBOM et rapport CVE si
`sbom-generator` est présent, archive, RPM (`scripts/build-rpm.sh`, depuis
`git archive HEAD` : seul le contenu commité est empaqueté).

`scripts/build-appimage.sh [--skip-build]` : bundle Flutter et CLI
compilée dans un AppDir (`AppRun` : interface par défaut, CLI avec `--cli`
ou via un lien nommé `check-script`), `.desktop`, icône et métadonnées
AppStream communs (`packaging/linux/`), puis `appimagetool` (PATH,
`APPIMAGETOOL`, ou téléchargé dans `build/appimage/`) → `dist/CheckScript-VERSION-ARCH.AppImage`.

`scripts/build-flatpak.sh [--install] [--skip-build]` : mêmes binaires,
manifeste `packaging/flatpak/fr.chla28.check_script_gui.yml` (runtime
GNOME 50, qui fournit GTK 3), `flatpak-builder` (ou `org.flatpak.Builder`),
runtime et SDK installés depuis Flathub pour l'utilisateur →
`dist/CheckScript-VERSION-ARCH.flatpak`. Dans le Flatpak,
`ProcessCommandRunner` lance les outils sur l'hôte (`hostInvocation` :
`flatpak-spawn --host --env=LC_ALL=C …`, présence vérifiée par `command -v`
sur l'hôte) ; les lanceurs placent `TMPDIR` dans le cache de l'application,
dont le chemin est identique dans le bac à sable et sur l'hôte.

Dans le Flatpak, le PATH de l'utilisateur sur l'hôte est lu une fois par
un shell de connexion (`bash -lc`, pour `~/.local/bin`, `~/bin`…) et chaque
outil est lancé par son *chemin absolu* résolu sur l'hôte : le portail
cherche l'exécutable avec son propre PATH minimal, pas celui de `--env`.

*Publication* (`.github/workflows/release.yml`) : à chaque tag `v*`, tests
(sans outils externes, pour des résultats indépendants des versions d'outils
des distributions), puis archive, AppImage et Flatpak (Ubuntu 24.04), RPM
(conteneur Fedora 44), et release GitHub avec les fichiers et l'extrait du
CHANGELOG. Flutter est figé (`FLUTTER_VERSION`).

Les deux scripts partagent `scripts/package-common.sh` et affichent la glibc
minimale requise par les binaires (2.34 actuellement : Rocky 9, runtimes
Flatpak) ; pour une AppImage largement compatible, construire sur la
distribution la plus ancienne visée.

Les specs neutralisent le strip et le debuginfo (ils corrompent les binaires
AOT Dart) ; le spec de l'interface désactive le scan automatique des
dépendances (moteur Flutter embarqué). Licence : LGPL-3.0-or-later
(`LICENSE`), reprise par les specs et les métadonnées AppStream.

La version figure dans `pubspec.yaml`, `gui/pubspec.yaml`,
`lib/src/version.dart` et `CHANGELOG.md` ; `build-dist.sh` signale un
écart entre les deux premiers fichiers Dart.
